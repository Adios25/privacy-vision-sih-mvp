# Codex SIH readiness execution brief

## Goal

Make Privvy submission-ready through measured evidence and controlled demos. Do not claim SIH readiness until every P0 item has an artifact or a clearly recorded blocker.

## Resume point

Read `evaluation/READINESS_STATUS.md` before continuing. It records work already completed and items still pending, so do not repeat completed baseline checks or treat templates as completed evidence. Continue from the first incomplete item and update the status report as evidence is produced.

## Rules

- Use only synthetic or explicitly permissioned data. Never commit real PII, raw screenshots, OCR output, API keys, browser profiles, or credentials.
- Do not invent accuracy, latency, browser, or server results. A claim requires a stored run artifact.
- Keep raw page values, raw OCR, original captures, and local profile values out of planner requests, logs, persisted state, and test artifacts.
- Redact screenshot pixels and structured page data independently before any network request.
- A failed privacy stage, failed leak check, or unavailable required local detector must block server transmission.
- Server actions are suggestions. Preserve local allowlisting, target revalidation, risk checks, approval gates, execution receipts, and post-action verification.
- Do not call a COCO `person` detection a face detection. Use `PERSON_REGION` unless a dedicated face detector is integrated and evaluated.
- QR/barcode redaction requires decoder evidence. Do not create QR masks from generic object shape or YOLO confidence.

## Work order

### 1. Freeze the baseline

1. Inspect `git status`, existing tests, package scripts, extension manifests, and server configuration.
2. Run the existing automated checks.
3. Create `evaluation/baseline/BASELINE.md` with date, commit hash, environment, exact commands, pass/fail status, and failures.
4. Do not alter unrelated user changes.

Acceptance:

- A reviewer can reproduce the baseline command list.
- The report clearly distinguishes passed tests from checks that were not run.

### 2. Complete the redaction evaluation set

Existing starter files:

- `evaluation/redaction-v1.json`
- `evaluation/README.md`
- `scripts/evaluate_redactions.py`

Expand the dataset with versioned synthetic fixtures and labels. Include:

- Aadhaar-like, PAN-like, passport, phone, email, names, addresses, passwords, and populated sensitive form values.
- Small, large, rotated, low-contrast, and partially occluded QR/barcodes.
- Negative visual cases: square icons, navigation controls, logos, dark controls, and QR-like graphics.
- Mixed application form, dashboard, document, and portal cases.

For every fixture, add a stable ID, category, source type, labels, coordinate system, and a statement that it is synthetic. Store image assets under `evaluation/fixtures/`; labels remain in dataset JSON. Do not use the evaluation set for model training.

Acceptance:

- Every case has a stable ID and expected text span or visual box.
- `python scripts/evaluate_redactions.py --predictions <file>` produces results from one command.
- Matching rules remain IoU >= 0.5 for text spans and visual boxes unless a documented, measured change is made.
- Results include TP, FP, FN, precision, recall, F1, false-redaction rate, and visual false-mask area fraction by category.

### 3. Build a prediction capture adapter and baseline results

Add a test adapter that runs the actual local detection pipeline against evaluation fixtures and writes prediction JSON in the schema documented by `evaluation/README.md`.

If browser-only APIs prevent headless execution, create a controlled manual capture procedure that exports only sanitized detection metadata: category, box/span, source, confidence, case ID, browser/OS/model metadata. Do not export raw OCR text or source images beyond the synthetic fixtures.

Run the evaluator and store baseline output under `evaluation/results/` with:

- Dataset version and fixture count.
- Detector/version/configuration.
- Browser, OS, hardware, and warm/cold state.
- Exact run command and date.
- Per-category metrics and false positives/false negatives.

Acceptance:

- Baseline numbers were generated by the evaluator from recorded predictions.
- No performance number in README, slides, or UI is manually typed without the corresponding result artifact.

### 4. Fix measured detection failures

Work from recorded false positives and false negatives only.

- Preserve decoder-only QR/barcode masks.
- Preserve `PERSON_REGION` semantics for COCO people detections.
- Document every threshold change with the before/after evaluation result.
- Add a regression fixture for each fixed failure.

Acceptance:

- New result files make regressions visible.
- No precision change increases false masks without documentation.

### 5. Complete the real sanitized server planner path

Inspect `server/server.py`, `server/vlm_bridge.py`, `server/CONFIGURATION.md`, and popup planning code.

Configure one supported provider path using environment variables or local configuration that is excluded from git. Keep deterministic local planning as a working fallback.

In the extension UI, visibly show:

- Planner mode: local or server.
- Provider/model identifier.
- Client scan time, redaction time, server/model time, and total planning time.
- Leak-check result and explicit per-scan consent state.

Add a sanitized request audit fixture or test that proves outbound data contains only redacted screenshot data and sanitized structured context. It must never contain known raw terms, raw OCR, unredacted image data, or profile values.

Acceptance:

- Server plan conforms to the allowlisted action protocol.
- Client rejects unrecognized actions and invented/stale targets.
- Server send is blocked on failed leak checks or absent consent.
- Local-only mode remains usable if server/network fails.

### 6. Add a judge-facing audit view

Extend the popup/side panel so a judge can understand the scan without DevTools. Show only synthetic demo data:

- Original synthetic view and redacted preview.
- Detection category, source, decoder verification state, active/disabled/manual masks.
- Eligible outbound context summary and leak-check status.
- Planner/provider/mode and timing values.
- Returned actions, approval outcome, execution receipt, and verification result.

Do not describe the payload hash as proof of privacy. Label it as an integrity fingerprint only.

### 7. Record Chrome and Firefox manual verification

Create `evaluation/manual-browser-verification.md` with a row per browser run. Record browser/version, OS, test date, extension build ID, tester, and pass/fail/evidence for:

1. Extension loads without manifest/runtime errors.
2. Scan and visible-tab capture work.
3. Local detector failures are understandable and block unsafe egress.
4. Manual overlays and mask toggles work.
5. Payload rebuilds after review.
6. Leak-check failure blocks server planning.
7. Sanitized server plan works after consent.
8. Local-only fallback works with network/server unavailable.
9. Safe action revalidates target before execution.
10. Submit/payment/delete actions require separate approval.

Do not mark a row passed unless it was manually performed in that browser.

### 8. Prepare three controlled demo workflows

Use the synthetic test portal. Create `evaluation/demo-workflows.md` with exact setup, task wording, expected masks, planner mode, approval boundary, expected action receipt, and reset procedure for:

1. Sensitive application form: detect/redact synthetic PII, prepare empty supported fields, stop before submission approval.
2. Download/export discovery: identify control, highlight it, request approval, click once, and verify outcome.
3. Status summary: redact identity data, summarize non-sensitive status, make no change.

Acceptance:

- Each workflow is repeatable without third-party websites.
- Screenshots and recordings contain synthetic data only.

### 9. Benchmark latency and resource use

Create `evaluation/benchmarks/` and record repeated scan measurements. Separate local scan, redaction, network, model/server, and total workflow time. Capture device/browser/OS, CPU/GPU availability, viewport/image size, page element count, warm/cold state, and repetition count.

Report median and p90 only when the repetition count supports it. Keep raw timing records beside summaries.

### 10. Update submission claims and checklist

Update README and presentation materials only from completed artifacts. State dataset version, case count, matching rule, browser/device conditions, known limitations, and exact planner mode.

Use this wording only when supported by evidence:

> Privvyy performs local page and visual analysis, applies reviewed masks to both screenshot and structured context, and requires a passing client leak check plus per-scan consent before sending sanitized context to the configured planner. Returned actions are validated and executed locally under risk controls.

## Final SIH-ready gate

Before declaring readiness, verify all of these are true:

- [ ] Baseline report exists.
- [ ] Versioned evaluation fixtures and labels exist.
- [ ] Reproducible detector predictions and evaluator results exist.
- [ ] Per-category precision, recall, F1, false-redaction rate, and visual mask-area metrics are recorded.
- [ ] QR/barcode and person/face claims exactly match the implemented detectors.
- [ ] Real sanitized server planning evidence exists.
- [ ] Local-only fallback evidence exists.
- [ ] Chrome and Firefox manual verification records exist.
- [ ] Three synthetic workflows are rehearsed and documented.
- [ ] Benchmarks include conditions and raw measurements.
- [ ] README/slides use only measured claims.

If any item is missing, report it as incomplete. Do not call the project SIH submission-ready.
